Operational Runbook

IBM MQ 9.2 → 9.3.0.21

Side-by-side upgrade of a standalone Queue Manager on Linux/RHEL. The goal is to prepare all MQ 9.3 code while the Queue Manager continues running on 9.2, keeping downtime limited to shutdown, physical backup, setmqm, and the first start on 9.3.

Source: WebSphere-MQ-9.2.0.4 Target: WebSphere-MQ-9.3.0.21 Linux / RHEL Standalone QM Side-by-side
Before use: replace <QM_NAME>, <SERVICE_NAME> and confirm the data/log paths used in your environment. Do not assume the new installation is named Installation4; confirm it with dspmqinst.

0. Important Path Convention Used in This Guide

Important: this guide uses one concrete upgrade example throughout the document. The current installation is /tech/WebSphere-MQ-9.2.0.4 and the new installation is /tech/WebSphere-MQ-9.3.0.21. If your server uses different paths, replace them before running the commands.

No shell variables are used in the examples. Commands intentionally show the full absolute paths so the active MQ installation is always visible.

1. PreFlight

The QM can remain RUNNING during this phase.

1.1 Confirm server, Queue Managers, and installations

hostname
/tech/WebSphere-MQ-9.2.0.4/bin/dspmq -o installation -o status
/tech/WebSphere-MQ-9.2.0.4/bin/dspmqinst
cat /etc/opt/mqm/mqinst.ini

1.2 Run mqconfig

cd /tech/WebSphere-MQ-latest/bin
./mqconfig

If any item shows FAIL, correct only the item reported by mqconfig, following your OS team standards.

Example: sysctl adjustment used in this environment

These values are examples from your environment, not a universal fix for every MAX FILES issue. If the problem is a per-process or per-user limit, also check ulimit -n and the files in /etc/security/limits.d/.
cd /etc/sysctl.d/
ls -ltr
vi 99-sysctl.conf

# ADD / CONFIRM
fs.file-max = 524288
kernel.threads-max = 32768

# Apply this file
sysctl -p /etc/sysctl.d/99-sysctl.conf

# Alternative: reload all sysctl configuration
# sysctl --system

# Recheck
cd /tech/WebSphere-MQ-latest/bin
./mqconfig

1.3 Create working directories

# Backup folder
mkdir -p /save/MQv92
chown mqm:mqm /save/MQv92

# RPM working folder
mkdir -p /save/MQv92/rpm
chown mqm:mqm /save/MQv92/rpm

# New MQ installation folder
mkdir -p /tech/WebSphere-MQ-9.3.0.21
chown mqm:mqm /tech/WebSphere-MQ-9.3.0.21

ls -ld /save/MQv92 /save/MQv92/rpm /tech/WebSphere-MQ-9.3.0.21

2. Logical Configuration Backup

The QM must be RUNNING. This is the correct time to run dmpmqcfg.
sudo -iu mqm

mkdir -p /save/MQv92/<QM_NAME>
chown mqm:mqm /save/MQv92/<QM_NAME>

# Objects / attributes
dmpmqcfg -m <QM_NAME> -a > /save/MQv92/<QM_NAME>/<QM_NAME>.mqsc

# Authorities as setmqaut commands
dmpmqcfg -m <QM_NAME> -x authrec -o setmqaut \
  > /save/MQv92/<QM_NAME>/<QM_NAME>_setmqaut.sh

# Channel authentication records
dmpmqcfg -m <QM_NAME> -x chlauth \
  > /save/MQv92/<QM_NAME>/<QM_NAME>_chlauth.mqsc

exit

Save the current inventory

/tech/WebSphere-MQ-9.2.0.4/bin/dspmq -o installation -o status > "/save/MQv92/dspmq-before.txt"
/tech/WebSphere-MQ-9.2.0.4/bin/dspmqinst > "/save/MQv92/dspmqinst-before.txt"
rpm -qa | grep '^MQSeries' | sort > "/save/MQv92/rpm-before.txt"
cp -p /etc/opt/mqm/mqinst.ini "/save/MQv92/mqinst.ini.before"

3. Download the binaries

The QM can still remain RUNNING on 9.2.

Generate the token in Artifactory. The value passed to --user is the ADMB account. In this guide the ADMB account is bpk32mk; each administrator must replace it with their own ADMB account. Use --ask-password so the Artifactory token is not written directly in the shell history.

cd /save/MQv92/rpm

wget --user=bpk32mk --ask-password \
'https://artifactory.mycloud.intrabpce.fr:443/artifactory/BIWMS-generic-ibm-websphere-upgrade/BIWMS/UPGRADE/IBM_MQ_9.3.0.15_LNX_X86-64.tar.gz'

wget --user=bpk32mk --ask-password \
'https://artifactory.mycloud.intrabpce.fr:443/artifactory/BIWMS-generic-ibm-websphere-upgrade/BIWMS/UPGRADE/9.3.0-IBM-MQ-LinuxX64-FP0021.tar.gz'

ls -lh

4. Install the MQ 9.3 Base Code

The MQ 9.2 Queue Manager can remain RUNNING. Installing the new MQ code does not migrate the Queue Manager yet.

4.1 Extract the media and accept the license

cd /save/MQv92/rpm
tar -zxvf IBM_MQ_9.3.0.15_LNX_X86-64.tar.gz

cd /save/MQv92/rpm/MQServer
./mqlicense.sh -accept

4.2 Install the MQ 9.3 base packages

Run the installation as root. This guide follows the installation method used in the existing operational procedure.

cd /save/MQv92/rpm/MQServer

rpm --prefix /tech/WebSphere-MQ-9.3.0.21 -ivh \
  MQSeriesRuntime-*.rpm \
  MQSeriesServer-*.rpm \
  MQSeriesJRE-*.rpm \
  MQSeriesJava-*.rpm \
  MQSeriesSamples-*.rpm \
  MQSeriesMan-*.rpm \
  MQSeriesGSKit-*.rpm \
  MQSeriesSDK-*.rpm \
  MQSeriesClient-*.rpm \
  MQSeriesMsg_fr-*.rpm

5. Install Fix Pack 9.3.0.21

The MQ 9.2 Queue Manager can still remain RUNNING. The new installation is being updated before the Queue Manager is associated with it.
cd /save/MQv92/rpm
tar -zxvf 9.3.0-IBM-MQ-LinuxX64-FP0021.tar.gz

Change to the directory containing the extracted Fix Pack RPM files, then run:

rpm --prefix /tech/WebSphere-MQ-9.3.0.21 -Uvh \
  MQSeriesRuntime-*.rpm \
  MQSeriesServer-*.rpm \
  MQSeriesJRE-*.rpm \
  MQSeriesJava-*.rpm \
  MQSeriesSamples-*.rpm \
  MQSeriesMan-*.rpm \
  MQSeriesGSKit-*.rpm \
  MQSeriesSDK-*.rpm \
  MQSeriesClient-*.rpm \
  MQSeriesMsg_fr-*.rpm

5.1 Validate the new installation before downtime

/tech/WebSphere-MQ-9.3.0.21/bin/dspmqver
/tech/WebSphere-MQ-9.3.0.21/bin/dspmqinst
rpm -qa | grep '^MQSeries' | sort | tee /save/MQv92/rpm-after-93021.txt

Do not continue until /tech/WebSphere-MQ-9.3.0.21/bin/dspmqver shows the expected level 9.3.0.21.

6. Start of the Downtime Window

DOWNTIME STARTS HERE. Put the host/QM into maintenance mode in Zabbix and stop applications that depend on the Queue Manager.

6.1 Stop the Queue Manager

If the systemd service is the standard shutdown method in your environment:

systemctl stop ""
/tech/WebSphere-MQ-9.2.0.4/bin/dspmq -o installation -o status

Expected status: STATUS(Ended normally).

If there is no reliable systemd service for stopping the Queue Manager:

sudo -iu mqm "/tech/WebSphere-MQ-9.2.0.4/bin/endmqm" -w ""
/tech/WebSphere-MQ-9.2.0.4/bin/dspmq -o installation -o status
Do not perform the physical backup or run setmqm while the QM is RUNNING.

7. Physical Backup with the QM Stopped

Confirm the actual data and log paths used in your environment. The examples below preserve the paths from the original runbook.

date > /save/MQv92/<QM_NAME>_cold-backup.timestamp

# MQ logs - site specific path
tar -cpzvf /save/MQv92/<QM_NAME>.log.bkp.tar.gz /logs/

# Queue manager/application data - site specific path
tar -cpzvf /save/MQv92/<QM_NAME>.qmgr.bkp.tar.gz /appli/

# MQ shared data / configuration
tar -cpzvf /save/MQv92/<QM_NAME>.VarMqm.bkp.tar.gz /var/mqm/

# Site scripts/configuration for mqm user
tar -cpzvf /save/MQv92/<QM_NAME>.HomeMqm.bkp.tar.gz /home/mqm/
For a consistent recovery, the Queue Manager data and recovery logs must represent the same point in time. If /logs or /appli are not the actual paths on this server, correct them before continuing.

8. Associate the Queue Manager with the MQ 9.3 Installation

8.1 Determine the actual name of the new installation

/tech/WebSphere-MQ-9.3.0.21/bin/dspmqinst

If the output shows Installation4, use that exact installation name in the next command. If it shows another name, use the value returned by dspmqinst.

8.2 Run setmqm from the new installation

sudo -iu mqm /tech/WebSphere-MQ-9.3.0.21/bin/setmqm -m <QM_NAME> -n Installation4

/tech/WebSphere-MQ-9.3.0.21/bin/dspmq -o installation -o status
Installation4 is only the example used in this guide. Replace it if dspmqinst reports a different installation name.

9. Update the symlink / systemd

9.1 Update the symlink

readlink -f /tech/WebSphere-MQ-latest
ln -sfn /tech/WebSphere-MQ-9.3.0.21 /tech/WebSphere-MQ-latest
readlink -f /tech/WebSphere-MQ-latest

9.2 Check the service

systemctl cat <SERVICE_NAME> | grep -E 'ExecStart|ExecStop'

If the unit already uses /tech/WebSphere-MQ-latest, there is no need to edit paths. If it is hardcoded to 9.2.0.4, update it to use the symlink or the new absolute path, then run:

systemctl daemon-reload

10. First Start on MQ 9.3

MIGRATION POINT OF NO RETURN: the first start of the QM using MQ 9.3 code performs the required migration. After the QM has been migrated, do not run setmqm back to 9.2 as a rollback. Recovery to MQ 9.2 requires restoring the state from before the migration.

If the systemd service points correctly to the MQ 9.3 installation:

systemctl start <SERVICE_NAME>
systemctl status <SERVICE_NAME> --no-pager

Validate immediately:

/tech/WebSphere-MQ-9.3.0.21/bin/dspmq -o installation -o status
sudo -iu mqm /tech/WebSphere-MQ-9.3.0.21/bin/runmqsc <QM_NAME> <<'MQSC'
DISPLAY QMGR CMDLEVEL
DISPLAY LSSTATUS(*) STATUS
DISPLAY CHSTATUS(*) STATUS
END
MQSC

tail -n 100 /var/mqm/qmgrs/<QM_NAME>/errors/AMQERR01.LOG

11. Make the MQ 9.3 Installation Primary

This is not required for setmqm or Queue Manager migration. Do this only after the Queue Managers that should migrate on this server have been validated.
/tech/WebSphere-MQ-9.3.0.21/bin/dspmqinst

If the current primary installation is Installation3 and the new installation is the one at /tech/WebSphere-MQ-9.3.0.21:

/tech/WebSphere-MQ-9.2.0.4/bin/setmqinst -x -n Installation3
/tech/WebSphere-MQ-9.3.0.21/bin/setmqinst -i -p /tech/WebSphere-MQ-9.3.0.21

/tech/WebSphere-MQ-9.3.0.21/bin/dspmqinst
Confirm the real installation names with dspmqinst before running setmqinst.

12. Final Validation

  1. ✓ dspmq shows Running and the new installation.
  2. ✓ /tech/WebSphere-MQ-9.3.0.21/bin/dspmqver shows 9.3.0.21.
  3. ✓ No new critical errors in the AMQERR01.LOG.
  4. ✓ Expected listener(s) and channels are operational.
  5. ✓ Applications can reconnect and complete the smoke test.
  6. ✓ The systemd service is active and enabled according to the environment standard.
  7. ✓ Remove Zabbix maintenance only after functional validation.
