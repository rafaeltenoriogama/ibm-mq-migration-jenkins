Runbook operacional

IBM MQ 9.2 → 9.3.0.21

Upgrade side-by-side de Queue Manager standalone em Linux/RHEL. A ideia é preparar todo o código 9.3 enquanto o Queue Manager continua em 9.2 e deixar o downtime apenas para parada, backup físico, setmqm e primeiro start em 9.3.

Origem: MQ 9.2.x Destino: MQ 9.3.0.21 Linux / RHEL Standalone QM Side-by-side
Antes de usar: troque <QM_NAME>, <SERVICE> e confirme os caminhos de dados/logs do seu ambiente. Não assuma que a nova instalação se chama Installation4; confirme com dspmqinst.

0. Variáveis do runbook

Defina uma vez para reduzir erro de digitação.

QM="<QM_NAME>"
SERVICE="<SERVICE>"                     # Ex.: websphere-MQ-RFDF01.service
OLD="/tech/WebSphere-MQ-9.2.0.4"
NEW="/tech/WebSphere-MQ-9.3.0.21"
BKP="/save/MQv92"
RPMDIR="$BKP/rpm"
SUFFIX="MQ93021"                         # somente letras/números, máx. 16 chars

1. PreFlight

QM pode continuar RUNNING nesta fase.

1.1 Confirmar servidor, Queue Managers e instalações

hostname
$OLD/bin/dspmq -o installation -o status
$OLD/bin/dspmqinst
cat /etc/opt/mqm/mqinst.ini

1.2 Executar mqconfig

cd /tech/WebSphere-MQ-latest/bin
./mqconfig

Se houver FAIL, corrija somente o item indicado pelo mqconfig e conforme o padrão do time de OS.

Exemplo: ajuste de sysctl usado no ambiente

Estes valores são um exemplo do seu ambiente, não uma correção universal para qualquer MAX FILES. Se o problema for limite por processo/usuário, confira também ulimit -n e os arquivos de /etc/security/limits.d/.
cd /etc/sysctl.d/
ls -ltr
vi 99-sysctl.conf

# ADD / CONFIRM
fs.file-max = 524288
kernel.threads-max = 32768

# Apply this file
sysctl -p /etc/sysctl.d/99-sysctl.conf

# Alternative: reload all sysctl configuration
# sysctl --system

# Recheck
cd /tech/WebSphere-MQ-latest/bin
./mqconfig

1.3 Criar diretórios de trabalho

mkdir -p "$BKP" "$RPMDIR"
mkdir -p "$NEW"

# Preserve the same owner/mode used by the current installation directory
chown --reference="$OLD" "$NEW"
chmod --reference="$OLD" "$NEW"

ls -ld "$OLD" "$NEW" "$BKP" "$RPMDIR"
Evite fazer chown -R mqm:mqm no diretório inteiro do produto sem uma razão específica. Os RPMs do MQ devem manter os owners/modes dos arquivos que instalam.

1.4 Confirmar dependências para multiple installations

command -v pax
command -v rpmbuild

Se faltarem, solicite/instale os pacotes necessários antes de continuar. A IBM exige ferramentas de repackaging para instalações MQ adicionais via RPM.

2. Backup lógico da configuração

QM deve estar RUNNING. Este é o momento para dmpmqcfg.
sudo -iu mqm

mkdir -p "$BKP/$QM"

# Objects / attributes
dmpmqcfg -m "$QM" -a > "$BKP/$QM/${QM}.mqsc"

# Authorities as setmqaut commands
dmpmqcfg -m "$QM" -x authrec -o setmqaut \
  > "$BKP/$QM/${QM}_setmqaut.sh"

# Channel authentication records
dmpmqcfg -m "$QM" -x chlauth \
  > "$BKP/$QM/${QM}_chlauth.mqsc"

exit

Guardar inventário atual

$OLD/bin/dspmq -o installation -o status > "$BKP/dspmq-before.txt"
$OLD/bin/dspmqinst > "$BKP/dspmqinst-before.txt"
rpm -qa | grep '^MQSeries' | sort > "$BKP/rpm-before.txt"
cp -p /etc/opt/mqm/mqinst.ini "$BKP/mqinst.ini.before"

3. Download dos binários

QM ainda pode continuar RUNNING em 9.2.

Gere o token no Artifactory. Evite colocar o token diretamente no histórico do shell.

cd "$RPMDIR"

wget --user=bpk32mk --ask-password \
'https://artifactory.mycloud.intrabpce.fr:443/artifactory/BIWMS-generic-ibm-websphere-upgrade/BIWMS/UPGRADE/IBM_MQ_9.3.0.15_LNX_X86-64.tar.gz'

wget --user=bpk32mk --ask-password \
'https://artifactory.mycloud.intrabpce.fr:443/artifactory/BIWMS-generic-ibm-websphere-upgrade/BIWMS/UPGRADE/9.3.0-IBM-MQ-LinuxX64-FP0021.tar.gz'

ls -lh

4. Instalar o código base 9.3 side-by-side

QM 9.2 continua RUNNING. Ainda não estamos migrando o Queue Manager.

4.1 Extrair e aceitar licença

cd "$RPMDIR"
tar -xzf IBM_MQ_9.3.0.15_LNX_X86-64.tar.gz

cd "$RPMDIR/MQServer"
./mqlicense.sh -accept

4.2 Criar RPMs únicos para a segunda instalação

Como o servidor já possui MQ 9.2, não instale os RPMs IBM originais com o mesmo nome. Use crtmqpkg.

cd "$RPMDIR/MQServer"
./crtmqpkg "$SUFFIX" "$NEW"

O comando informa o diretório onde criou os RPMs repackaged. Entre nesse diretório.

cd <OUTPUT_DIRECTORY_FROM_crtmqpkg>
ls -lh MQSeries*.rpm

4.3 Instalar os mesmos componentes necessários no servidor

Use os RPMs gerados pelo crtmqpkg. A lista abaixo é um exemplo baseado no seu runbook. Confirme os componentes atuais em $BKP/rpm-before.txt.
rpm -ivh \
  MQSeriesRuntime_${SUFFIX}-*.rpm \
  MQSeriesServer_${SUFFIX}-*.rpm \
  MQSeriesJRE_${SUFFIX}-*.rpm \
  MQSeriesJava_${SUFFIX}-*.rpm \
  MQSeriesSamples_${SUFFIX}-*.rpm \
  MQSeriesMan_${SUFFIX}-*.rpm \
  MQSeriesGSKit_${SUFFIX}-*.rpm \
  MQSeriesSDK_${SUFFIX}-*.rpm \
  MQSeriesClient_${SUFFIX}-*.rpm

Se o pacote de mensagens em francês fizer parte do padrão do servidor, instale também o RPM repackaged correspondente a MQSeriesMsg_fr, confirmando primeiro o nome exato com ls.

5. Aplicar maintenance 9.3.0.21 na nova instalação

QM 9.2 ainda pode continuar RUNNING, porque estamos aplicando maintenance somente à nova instalação 9.3, sem QMs associados a ela.
cd "$RPMDIR"
mkdir -p fp0021
cd fp0021

tar -xzf ../9.3.0-IBM-MQ-LinuxX64-FP0021.tar.gz
ls -la

Para uma instalação adicional, use crtmqfp com o mesmo suffix utilizado no crtmqpkg.

cd <DIRECTORY_CONTAINING_crtmqfp>
./crtmqfp "$SUFFIX" "$NEW"

cd <OUTPUT_DIRECTORY_FROM_crtmqfp>
ls -lh MQSeries*.rpm
Aplique somente updates correspondentes aos componentes já instalados. O procedimento IBM de maintenance via RPM usa rpm -ivh nos RPMs de update; não substitua por -Uvh sem validar o packaging do seu ambiente.
# Example: install the generated update RPMs that match your installed components
rpm -ivh <GENERATED_9.3.0.21_UPDATE_RPMS>

5.1 Validar a nova instalação antes do downtime

$NEW/bin/dspmqver
$NEW/bin/dspmqinst
rpm -qa | grep '^MQSeries' | sort | tee "$BKP/rpm-after-93021.txt"

Não continue até confirmar que $NEW/bin/dspmqver mostra o nível esperado 9.3.0.21.

6. Início da janela de downtime

DOWNTIME COMEÇA AQUI. Coloque o host/QM em maintenance no Zabbix e pare aplicações que dependem do Queue Manager.

6.1 Parar o Queue Manager

Se o serviço systemd é o método oficial do ambiente:

systemctl stop "$SERVICE"
$OLD/bin/dspmq -o installation -o status

O esperado é STATUS(Ended normally).

Se não houver um serviço systemd confiável para a parada:

sudo -iu mqm "$OLD/bin/endmqm" -w "$QM"
$OLD/bin/dspmq -o installation -o status
Não faça o backup físico nem execute setmqm enquanto o QM estiver RUNNING.

7. Backup físico com o QM parado

Confirme os caminhos reais de dados e logs do seu ambiente. Os exemplos abaixo mantêm os paths usados no runbook original.

date > "$BKP/${QM}_cold-backup.timestamp"

# MQ logs - site specific path
tar -cpzvf "$BKP/${QM}.log.bkp.tar.gz" /logs/

# Queue manager/application data - site specific path
tar -cpzvf "$BKP/${QM}.qmgr.bkp.tar.gz" /appli/

# MQ shared data / configuration
tar -cpzvf "$BKP/${QM}.VarMqm.bkp.tar.gz" /var/mqm/

# Site scripts/configuration for mqm user
tar -cpzvf "$BKP/${QM}.HomeMqm.bkp.tar.gz" /home/mqm/
Para recuperação consistente, dados e recovery logs do QM precisam representar o mesmo ponto no tempo. Se /logs ou /appli não forem os caminhos reais deste servidor, corrija antes de continuar.

8. Associar o Queue Manager à instalação 9.3

8.1 Descobrir o nome real da nova instalação

$NEW/bin/dspmqinst

Exemplo: se o output mostrar Installation4, use exatamente esse nome abaixo.

NEW_INST="Installation4"   # EXAMPLE — use the value returned by dspmqinst

8.2 Executar setmqm a partir da NOVA instalação

sudo -iu mqm "$NEW/bin/setmqm" -m "$QM" -n "$NEW_INST"

$NEW/bin/dspmq -o installation -o status

Confirme que o QM agora aparece associado à nova instalação.

9. Atualizar symlink / systemd

9.1 Atualizar o symlink

readlink -f /tech/WebSphere-MQ-latest
ln -sfn "$NEW" /tech/WebSphere-MQ-latest
readlink -f /tech/WebSphere-MQ-latest

9.2 Conferir o serviço

systemctl cat "$SERVICE" | grep -E 'ExecStart|ExecStop'

Se o unit já usa /tech/WebSphere-MQ-latest, não é necessário editar paths. Se ele estiver hardcoded em 9.2.0.4, atualize para o symlink ou para o novo path e então:

systemctl daemon-reload

10. Primeiro start em MQ 9.3

PONTO DE NÃO RETORNO DA MIGRAÇÃO: o primeiro start do QM com o código 9.3 realiza a migração necessária. Depois que o QM foi migrado, não faça setmqm de volta para 9.2 como rollback. A recuperação para 9.2 exige restaurar o estado anterior à migração.

Se o serviço systemd aponta corretamente para a instalação 9.3:

systemctl start "$SERVICE"
systemctl status "$SERVICE" --no-pager

Valide imediatamente:

$NEW/bin/dspmq -o installation -o status
sudo -iu mqm "$NEW/bin/runmqsc" "$QM" <<'MQSC'
DISPLAY QMGR CMDLEVEL
DISPLAY LSSTATUS(*) STATUS
DISPLAY CHSTATUS(*) STATUS
END
MQSC

tail -n 100 "/var/mqm/qmgrs/$QM/errors/AMQERR01.LOG"

11. Tornar a instalação 9.3 primary

Isso não é necessário para o setmqm/migração do QM. Faça depois que os QMs que devem migrar neste servidor estiverem validados. Em servidor com vários QMs, normalmente deixe para depois de mover todos eles.
$NEW/bin/dspmqinst

Se a política do ambiente é tornar a nova instalação primary:

# Example only: confirm the real old installation name first
OLD_INST="Installation3"

$OLD/bin/setmqinst -x -n "$OLD_INST"
$NEW/bin/setmqinst -i -p "$NEW"

$NEW/bin/dspmqinst

12. Validação final

  1. ✓ dspmq mostra Running e a nova instalação.
  2. ✓ $NEW/bin/dspmqver mostra 9.3.0.21.
  3. ✓ Sem erros críticos novos no AMQERR01.LOG.
  4. ✓ Listener(s) e channels esperados estão operacionais.
  5. ✓ Aplicações conseguem reconectar e fazer o smoke test.
  6. ✓ Serviço systemd está ativo e habilitado conforme padrão do ambiente.
  7. ✓ Remover maintenance do Zabbix somente após validação funcional.
