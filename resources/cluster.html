Cluster IBM MQ com 6 servidores, do zero

Guia prático e visual para montar um Queue Manager Cluster simples: dois Full Repositories, quatro Partial Repositories, canais de cluster, filas compartilhadas pelo cluster, teste de distribuição e diagnóstico.

1

Primeiro: o que estamos construindo?

Um IBM MQ Cluster permite que Queue Managers publiquem informações sobre si e sobre filas que hospedam, para que outros Queue Managers consigam localizar e encaminhar mensagens sem você manter manualmente uma definição de QREMOTE + XMITQ + SDR/RCVR para cada caminho.

6

Queue Managers

Um por servidor neste laboratório. Cada um continua sendo um Queue Manager independente.

2

Full Repositories

Mantêm a visão completa do cluster. Usaremos QMFR01 e QMFR02.

4

Partial Repositories

Guardam apenas as informações de cluster necessárias ao seu funcionamento normal.

Cluster ≠ HA do Queue Manager. Se QMAP03 morrer, ele não “vira” automaticamente QMAP04. MQ Cluster ajuda em descoberta, roteamento e workload entre instâncias de filas. Alta disponibilidade do próprio QM envolve outras tecnologias, como RDQM, Native HA/containers ou outras arquiteturas.

Por que usar o nome do CLUSRCVR no CLUSSDR?

O CLUSSDR manual precisa apontar para um Full Repository e seu nome deve coincidir com o nome do CLUSRCVR do Queue Manager de destino.

No QMFR01:
CLUSRCVR = CLAPP01.QMFR01

No QMAP01:
CLUSSDR = CLAPP01.QMFR01
CONNAME = mq01.lab.local(1414)
Regra mental: o nome do canal manual descreve quem recebe. Se estou no QMAP01 e quero chegar ao QMFR01, defino um CLUSSDR(CLAPP01.QMFR01).
4

Pré-requisitos

  • IBM MQ instalado nos seis servidores.
  • Usuário administrativo mqm disponível e autorizado.
  • DNS funcionando entre os seis hosts, ou entradas equivalentes em /etc/hosts.
  • TCP/1414 liberado entre os seis servidores.
  • Evitar NAT entre os membros, se possível; o CONNAME publicado deve ser alcançável pelos demais.
  • Relógios sincronizados (NTP/chrony) para facilitar logs e troubleshooting.
Linux — teste básico antes de MQ
# Em cada host, confirme que os nomes resolvem
getent hosts mq01.lab.local mq02.lab.local mq03.lab.local mq04.lab.local mq05.lab.local mq06.lab.local

# Depois que os listeners estiverem ativos, teste portas
nc -vz mq01.lab.local 1414
nc -vz mq02.lab.local 1414
Não use como “solução” de laboratório: ALTER QMGR CHLAUTH(DISABLED). Se segurança bloquear algum canal, diagnostique a regra e corrija a autorização. Desabilitar CHLAUTH globalmente mascara o problema e cria uma configuração ruim para reaproveitar depois.

Criar o listener TCP em cada QM

O listener recebe conexões de canais. Como cada QM está em um servidor diferente, todos podem usar a mesma porta 1414.

Modelo — troque apenas o nome do QM no runmqsc
runmqsc QMFR01

DEFINE LISTENER(LISTENER.TCP) TRPTYPE(TCP) PORT(1414) CONTROL(QMGR)
START LISTENER(LISTENER.TCP)
DISPLAY LSSTATUS(LISTENER.TCP) ALL
END
ServidorComando de entrada
mq01runmqsc QMFR01
mq02runmqsc QMFR02
mq03runmqsc QMAP01
mq04runmqsc QMAP02
mq05runmqsc QMAP03
mq06runmqsc QMAP04

CONTROL(QMGR) faz o listener acompanhar o ciclo de vida do Queue Manager após configurado.

Transformar QMFR01 e QMFR02 em Full Repositories

Somente os dois primeiros QMs recebem ALTER QMGR REPOS(CLAPP01). Os outros quatro ficam como partial repositories por padrão.

QMFR01

mq01
runmqsc QMFR01
ALTER QMGR REPOS(CLAPP01)
DISPLAY QMGR REPOS REPOSNL
END

QMFR02

mq02
runmqsc QMFR02
ALTER QMGR REPOS(CLAPP01)
DISPLAY QMGR REPOS REPOSNL
END
O que mudou? Esses dois QMs passam a manter a visão completa das definições de cluster. Os quatro QMAPxx não precisam de um comando dizendo “sou partial”; eles simplesmente não recebem REPOS(CLAPP01).

Definir os canais de cluster

8.1 — Cada QM publica seu próprio CLUSRCVR

Esse canal anuncia ao cluster “é assim que vocês chegam até mim”. O CONNAME aponta para o próprio host.

8.2 — Full Repositories se conectam entre si

QMFR01 tem CLUSSDR para QMFR02; QMFR02 tem CLUSSDR para QMFR01.

8.3 — Cada Partial ganha um CLUSSDR de bootstrap

Usaremos QMFR01 para QMAP01/02 e QMFR02 para QMAP03/04. Não crie manualmente canais entre todos os pares.

8.1 CLUSRCVR — execute em todos os QMs

QMFR01

runmqsc QMFR01
DEFINE CHANNEL(CLAPP01.QMFR01) CHLTYPE(CLUSRCVR) +
  TRPTYPE(TCP) +
  CONNAME('mq01.lab.local(1414)') +
  CLUSTER(CLAPP01) +
  DESCR('Cluster receiver QMFR01')

QMFR02

runmqsc QMFR02
DEFINE CHANNEL(CLAPP01.QMFR02) CHLTYPE(CLUSRCVR) +
  TRPTYPE(TCP) +
  CONNAME('mq02.lab.local(1414)') +
  CLUSTER(CLAPP01) +
  DESCR('Cluster receiver QMFR02')

Criar uma fila realmente “clusterizada”

Uma fila só passa a ser publicada no cluster quando você a define com CLUSTER(CLAPP01). Para visualizar workload, criaremos a mesma fila local em QMAP03 e QMAP04.

No QMAP03

runmqsc QMAP03
DEFINE QLOCAL(APP.REQUEST) +
  CLUSTER(CLAPP01) +
  DEFBIND(NOTFIXED) +
  DEFPSIST(YES) +
  DESCR('Clustered application request queue')

No QMAP04

runmqsc QMAP04
DEFINE QLOCAL(APP.REQUEST) +
  CLUSTER(CLAPP01) +
  DEFBIND(NOTFIXED) +
  DEFPSIST(YES) +
  DESCR('Clustered application request queue')

CLUSTER(CLAPP01)

Publica a definição para o cluster. Outros QMs podem descobrir que APP.REQUEST existe nesses dois destinos.

DEFBIND(NOTFIXED)

Quando a aplicação não força outra opção de bind, permite reavaliar o destino a cada MQPUT, útil para demonstrar distribuição entre instâncias.

Duas filas com o mesmo nome no cluster não significam “a mesma fila física”. São duas instâncias locais distintas de APP.REQUEST, uma no QMAP03 e outra no QMAP04.

Testar descoberta e distribuição

Usaremos QMAP01 como produtor. Ele não possui uma fila local APP.REQUEST; portanto precisa localizar as instâncias publicadas por QMAP03 e QMAP04.

1. Ver se QMAP01 conhece a fila

runmqsc QMAP01
DISPLAY QCLUSTER(APP.REQUEST) ALL

Em um partial repository, nem toda fila remota precisa aparecer antes de ser usada; o conhecimento é mantido sob demanda.

2. Enviar várias mensagens a partir de QMAP01

shell como mqm em mq03
amqsput APP.REQUEST QMAP01

mensagem-01
mensagem-02
mensagem-03
mensagem-04
mensagem-05
mensagem-06
mensagem-07
mensagem-08
<ENTER em uma linha vazia para terminar>

3. Ver a profundidade das duas filas

QMAP03
echo "DISPLAY QLOCAL(APP.REQUEST) CURDEPTH IPPROCS OPPROCS" | runmqsc QMAP03
QMAP04
echo "DISPLAY QLOCAL(APP.REQUEST) CURDEPTH IPPROCS OPPROCS" | runmqsc QMAP04

4. Consumir

nos servidores 5 e 6
# server 5
amqsget APP.REQUEST QMAP03

# server 6
amqsget APP.REQUEST QMAP04
Importante: não espere necessariamente uma divisão matemática 4/4 em todo cenário. O algoritmo de cluster considera disponibilidade, estado dos canais e atributos de workload. Este laboratório serve para provar descoberta + múltiplos destinos.

Como o cluster “pensa”

DESCoberta

Repository

QMFR01/QMFR02 conhecem os membros e recursos publicados. Os partials consultam repository information conforme precisam.

ENDEREÇO

CLUSRCVR

É a publicidade do próprio Queue Manager: nome de canal, host/porta e associação com o cluster.

BOOTSTRAP

CLUSSDR

A definição manual dá ao QM um primeiro caminho até um Full Repository. Depois o cluster aprende rotas adicionais.

Sem cluster

Você normalmente precisa desenhar explicitamente caminhos de distributed queuing: QREMOTE, XMITQ, SDR/RCVR e naming correspondente para cada rota.

Com cluster

Você publica Queue Managers e filas no cluster. O repository service distribui as informações necessárias e o workload algorithm pode escolher entre múltiplas instâncias compatíveis.

14

Antes de chamar isso de produção

  • TLS nos canais de cluster.
  • Políticas CHLAUTH e autoridades MQ bem definidas.
  • Dois Full Repositories em hosts/domínios de falha distintos.
  • DNS estável e hostnames publicados no CONNAME.
  • Monitorização de canais, listeners, depths e error logs.
  • Dead-letter queue e procedimento operacional para DLQ.
  • Backups/configuração versionada e scripts MQSC idempotentes.
  • Planejar MAXMSGL, MAXDEPTH e persistência conforme aplicação.
  • Definir estratégia de workload: DEFBIND, CLWLPRTY, CLWLRANK, CLWLUSEQ.
  • Separar “cluster para roteamento” de “HA do Queue Manager”.
  • Testar perda de um Full Repository e recuperação.
  • Testar indisponibilidade de uma instância da fila.
